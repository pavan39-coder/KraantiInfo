# KraantiInfo

KraantiInfo is a MERN monorepo for a professional Indian news publication with an editorial dashboard and an article-aware assistant. It uses MongoDB when configured and otherwise runs with clearly labelled demo content.

## Run locally

Requirements: Node.js 20+ and MongoDB (optional for demo mode; required for persistence).

1. Install all workspace dependencies once from the project root:

   ```sh
   npm install
   ```
2. Copy `server/.env.example` to `server/.env`. Set `MONGO_URI` if you want MongoDB persistence. Keep future provider credentials server-side.
3. Start both applications:

   ```sh
   npm run dev
   ```

The React client is at `http://localhost:5173` (Vite automatically uses the next free port if occupied); the Express API is at `http://localhost:5000`.

Useful root commands: `npm run dev` starts both apps, `npm run dev:server` or `npm run dev:client` starts one app, `npm test` runs the backend tests, and `npm run check` runs tests plus the production frontend build.

Production requires `CLIENT_ORIGIN` to contain the deployed frontend origin, plus MongoDB and admin credentials/secrets in the backend environment. The server protects admin routes unless it is explicitly started with `NODE_ENV=development`; `npm run dev` sets development mode for local work. The 30-minute scheduler runs in the API process, so use an always-on backend service rather than a sleeping/serverless-only backend.

## Deploy frontend to Vercel and backend to Render

The repository includes a root `vercel.json` and a Render Blueprint at `render.yaml`.

1. Push this repository to GitHub. Import it in Vercel with the repository root as the project root. The config builds the `client` workspace and publishes `client/dist`.
2. Add the Vercel environment variable `VITE_API_URL` with the Render API URL plus `/api`, for example `https://wakeupindia.onrender.com/api`. Redeploy after adding it. This value is public frontend configuration; do not put provider keys here.
3. In Render, create a Blueprint from the repository and use `render.yaml`. It runs the Express API as an always-on Starter web service, serves `/api/health`, and keeps the 30-minute scheduler alive. A free Render web service sleeps after 15 minutes without inbound requests, so it is not suitable for this scheduler.
4. In Render, fill the prompted values: `CLIENT_ORIGIN` with the exact Vercel production origin (no `/` at the end), `MONGO_URI` with a MongoDB Atlas connection string, `ADMIN_EMAIL`, `ADMIN_PASSWORD`, and `OPENROUTER_API_KEY`. `JWT_SECRET` is generated by the Blueprint. Add `NEWSDATA_API_KEY` only if an enabled NewsData.io source needs it. Keep all provider and database secrets in Render, never in Vercel.
5. In MongoDB Atlas, allow the Render service to connect, then sign in to `/admin` using the Render admin credentials. Add sources, assign a reliability score based on the publisher's trustworthiness, and enable only feeds you are allowed to use. Confirm `/api/health` reports the database connected and the news/AI switches enabled.

Automatic selection and publishing are enabled in the Render Blueprint. Each successful 30-minute cycle asks AI to select the single best candidate, then attempts to publish it automatically when the source is approved and reliable (75+), the source is no more than 24 hours old, the description has at least 80 characters, and the generated article is complete. Political, health, crime, and other sensitive stories remain in review. A cycle can publish zero stories when no safe candidate is available or the AI provider/collection fails; the scheduler cannot guarantee a publication in those cases. Published items are labelled as AI-assisted and not independently verified, and retain their source link. This does not replace checking the publisher's reuse/license terms. Availability, rate limits, and quality of OpenRouter free models can vary.

The first scheduled collection starts after the configured interval. Add and enable at least one approved source in the newsroom; an empty source list means the recurring collector has nothing to fetch. You can trigger a collection manually from the newsroom after setup.

## Deploy the full stack on one VPS with Docker

The repository includes a Docker Compose deployment for a VPS (including Hostinger VPS): React/Nginx, the Express API and scheduled collector, MongoDB, and Caddy for HTTPS. Point your domain's DNS A record at the VPS IP and allow inbound ports 80 and 443. On the server, install Docker Compose, copy this project, copy `deploy.env.example` to `deploy.env`, and set the domain, MongoDB credentials, admin credentials, a random JWT secret, and a newly created OpenRouter API key. Use a long URL-safe alphanumeric MongoDB password. The example enables the news engine, AI processing, and guarded auto-publishing; first configure MongoDB and approved sources in the newsroom. Start with `docker compose --env-file deploy.env up -d --build`. MongoDB is only attached to the private Docker network; use backups for the `mongo-data` volume. Never commit `deploy.env`.

## Current functionality

- Responsive editorial homepage, category filtering, search, article reading view, and related stories.
- Article-context assistant with a demo response. Connect a licensed LLM provider on the server before using real model responses.
- Admin newsroom dashboard with source status, collection controls, and collected-source candidates.
- Editorial workflow: an AI drafting agent can create original articles from source headlines and short metadata. Editors can edit drafts, submit them for review, and explicitly publish or reject them. Manual publishing requires fact-check and attribution confirmations, plus an extra confirmation for sensitive categories. The optional auto-publish path is separately guarded by strict low-risk criteria and marks published articles as not independently verified.
- Server-side collector adapters for NewsData.io, GDELT DOC API, approved RSS, and government RSS feeds. It normalizes source metadata and deduplicates by canonical URL and matching headline/day before saving candidates to MongoDB.
- External discovery is disabled by default (`NEWS_ENGINE_ENABLED=false`). When enabled with MongoDB connected, enabled sources are collected on the server schedule (30 minutes by default); an editor can also trigger a collection from the newsroom. Demo discovery remains separate and makes no external requests.
- The drafting agent sends only collected metadata (headline, short description, source attribution/link, date and category) to the configured server-side OpenRouter API. It can compare a batch of recent candidates, select one likely to interest readers, and create an original brief with verification notes. It does not fetch full publisher articles.
- Production admin endpoints require a JWT. Configure `ADMIN_EMAIL`, `ADMIN_PASSWORD`, and a random `JWT_SECRET` of at least 32 characters in server/deployment secrets. Development mode keeps the sample newsroom accessible for local preview.
- Optional Blogger syndication sends each article to Blogger only after the article has been published on KraantiInfo. Both scheduled auto-published articles and manually approved articles use the same server-side integration. Failed transfers are recorded on the KraantiInfo article and can be retried from the newsroom; Blogger failures do not undo a successful KraantiInfo publication.

## Connecting real news providers

To prepare the collector:

1. Set `MONGO_URI` to a running MongoDB database.
2. For NewsData.io, configure `NEWSDATA_API_KEY` in `server/.env` (or deployment secrets). The key is never sent to React. GDELT needs no key. Add RSS and government feeds using their public HTTPS feed URLs.
3. In the newsroom, add each source, check its terms for your intended use, and enable it. A NewsData.io search query or GDELT query can be set as the source's optional search query; RSS sources require their feed URL.
4. Only after reviewing licensing, attribution, caching/storage, and commercial-use requirements, set `NEWS_ENGINE_ENABLED=true` on the server and restart it. The collector then polls enabled sources every `NEWS_COLLECTION_INTERVAL_MINUTES` (30 by default; minimum 5), or on an editor-triggered run.
5. Review collected candidates and source links. Do not republish full publisher articles unless the applicable license permits it.

The collector stores normalized metadata and short provider/feed descriptions, not full article text. NewsData.io plan freshness and content limits depend on the selected plan. GDELT and feeds have their own coverage and terms; check current provider documentation and source terms before production use.

## AI editorial drafts

Set `OPENROUTER_API_KEY` and `OPENROUTER_MODEL` (defaults to `openrouter/free`) in `server/.env`; never add provider credentials to client/Vite environment variables. Optional fallback models can be configured with `OPENROUTER_FALLBACK_MODELS`, but each fallback attempt consumes another request. Automatic batch selection uses one API request per cycle and does not retry alternate models, to conserve free-tier requests. Free model availability, rate limits, and output quality can vary; check your OpenRouter account's current limits. AI generation is not fact-checking.

### Automatic AI selection and drafting

Set `AI_AUTO_PROCESSING_ENABLED=true` on the backend to compare recent candidates after each scheduled or manually triggered collection and create at most one AI-written article per cycle. Set `AI_AUTO_PUBLISH_ENABLED=true` to enable the guarded auto-publish path described above; otherwise generated stories enter the human review queue. Editors can also click **Process AI candidates now** to run the same step without fetching sources. The AI receives metadata only and returns its selection reason and verification notes. Its choice is an estimate of reader interest, not a measure based on KraantiInfo audience analytics.

The combined selection-and-draft request is designed to use one OpenRouter request per 30-minute cycle (48 scheduled cycles/day), which is close to free-provider daily limits; manual runs, retries, and provider-side limits can still cause quota errors. The server must remain running for scheduled collection. A local development backend stops when the computer is off.

### Mirror published articles to Blogger

KraantiInfo can syndicate the same article to a Blogger blog after it has been published on KraantiInfo. The integration uses the Blogger API and server-side Google OAuth refresh-token credentials; do not put these secrets in the React/Vercel client or commit them.

1. In Google Cloud Console, create/select a project, enable **Blogger API v3**, configure the OAuth consent screen, and create an OAuth client. Add `https://developers.google.com/oauthplayground` as an authorized redirect URI if using Google's OAuth 2.0 Playground to authorize the blog owner.
2. In OAuth 2.0 Playground settings, select **Use your own OAuth credentials**, use the OAuth client ID/secret, keep the flow server-side and access type offline, then authorize `https://www.googleapis.com/auth/blogger`. Exchange the authorization code and securely copy the refresh token. A Google Cloud OAuth app left in external **Testing** mode issues refresh tokens that expire after 7 days; production use needs the consent app moved to production (and any Google verification requirements completed).
3. Find the Blogger blog ID from the Blogger API (`GET /blogger/v3/users/self/blogs`) or a Blogger API response. Put these values in Render's backend environment: `BLOGGER_BLOG_ID`, `BLOGGER_CLIENT_ID`, `BLOGGER_CLIENT_SECRET`, `BLOGGER_REFRESH_TOKEN`, `BLOGGER_AUTO_PUBLISH_ENABLED=true`, and `PUBLIC_SITE_URL=https://kraantiinfo.vercel.app` (use the site's canonical URL if it changes).
4. Redeploy the backend. The newsroom overview shows whether Blogger sync is connected. New KraantiInfo publications are then mirrored automatically. Existing successful KraantiInfo publications are not bulk-copied. Failed Blogger transfers remain visible in the article's `bloggerSync` state and can be retried with **Retry failed Blogger posts** in the newsroom.

The sync uses a unique Blogger label derived from the KraantiInfo article ID, so retries can find a post created before a network failure and avoid creating a duplicate. Blogger API post insertion requires OAuth authorization with the Blogger scope. References: [Blogger posts insert](https://developers.google.com/blogger/docs/3.0/reference/posts/insert), [Blogger OAuth authorization](https://developers.google.com/blogger/docs/3.0/using), [Google refresh-token expiry](https://developers.google.com/identity/protocols/oauth2/).

## MongoDB

Set `MONGO_URI` in `server/.env`, for example to a local database URL, to enable article and source persistence. The server starts in demo/read-only mode without a database and logs the connection status.
